# Core tables and module contracts

The shared tables every feature builds on, and the interfaces and events between modules. Field lists come from Appendix 2 of the brief. The SQL for the tables is in [V2__core_tables.sql](../backend/src/main/resources/db/migration/V2__core_tables.sql).

Items marked **Decide** are still open for the team.

Backend packages (already in the skeleton under `com.scrooge.crm`): `users` (F1), `clients` (F2 clients, accounts, identity), `verification` (F2 wealth), `transactions` (F3), `recommendations` (F4), `retention` (F5), `cases` (F6), `shared.*`.

## Part A: core tables and the transaction file (meeting 1)

### A1. Conventions every table follows

- **IDs** are UUIDv7, stored as Postgres `uuid` and generated by Hibernate (`@UuidGenerator`, version 7 style). They sort by creation time, can't be guessed, and need no custom code. Postgres 16 can't generate v7 itself, so the application always supplies the ID. Transaction IDs are the exception: they're text from the core-banking file. Reasoning is in [decisions.md](decisions.md), D8.
- **Enums** are upper-case strings with a `CHECK` constraint (`'SAVINGS'`, not `'Savings'`). They map to Java enums with `@Enumerated(EnumType.STRING)`. The API returns the same upper-case values and the frontend formats them for display.
- **Money** is `numeric(14,2)` in the database, `BigDecimal` in Java, and a string in JSON (`"1500.00"`). Never use `double`.
- **Time** is `timestamptz` (stored in UTC) and `Instant` in Java. A plain date with no time, such as a date of birth or an account's opening date, is `date` / `LocalDate`. "Today" and business days are worked out in `Asia/Singapore` by the shared `SgCalendar` helper.
- **Every mutable row** has `created_at`, `updated_at` and `version` (optimistic locking via `@Version`). `updated_at` is set by Hibernate (`@UpdateTimestamp`); the column default only covers inserts. Two agents editing the same client gets a 409, not a silent overwrite.
- **Nothing that matters is hard-deleted.** Closing an account sets its status to `CLOSED`. Erasing a client keeps the row but sets its PII columns to NULL and sets `erased_at`. A check constraint requires the PII while `erased_at` is empty. Erasure also closes the client's accounts. Transactions and audit rows stay, because a bank has to keep them; the PII inside audit rows is handled by crypto-shredding (B2, `shared.audit`). Users are never hard-deleted either: "delete user" sets `deleted_at` and deletes the Cognito user (`AdminDeleteUser`, so the email can be used again), because cases and audit rows still reference the row. "Disable user" is the brief's separate operation and only disables the login. See [decisions.md](decisions.md), D12.
- **PII at rest:** the whole database is encrypted with KMS (Aurora storage encryption). Free-text fields that can hold anything (case descriptions, intervention notes) are also encrypted in the application. Email and phone are not encrypted in the application, because they need unique indexes. Logs mask them (`maskValue`, ported from the demo).

### A2. The five tables

| Table | Owner (only writer) | Read by | Notes |

| `accounts` | F2 (`clients`) | F3, F4, F5 | All 8 Appendix 2 fields, plus `source` (`AGENT`/`RECOMMENDATION`), `source_ref` and `closed_at`. Opens as `PENDING`. |
| `transactions` | F3 (`transactions`) | F4, F5, F6 | Appendix 2 fields, plus `account_id`, `currency`, `import_run_id` and `imported_at`. The primary key is the core-banking ID, which is what makes re-imports safe. |
| `cases` | F6 (`cases`) | F4, F5 | `agent_id` is the assignee and `created_by` is who raised it. `description_enc` holds the encrypted text. A transaction dispute must have a `transaction_id`. |

Columns and constraints in full are in the SQL draft. The ones that need agreement:

| Column | Proposal | Why |
|---|---|---|
| `clients.gender` | `MALE`, `FEMALE`, `NON_BINARY`, `PREFER_NOT_TO_SAY` | The brief's four options. |
| `clients.phone` | E.164 with the `+`, 10–15 digits, e.g. `+6591234567` | The brief's example format. Normalising before saving makes the unique index work. |
| `clients.identity_status` | `PENDING`, `VERIFIED`, `FAILED`, `MANUAL_REVIEW` | Same as the demo. |
| `accounts.status` | `PENDING`, `ACTIVE`, `INACTIVE`, `CLOSED` | The brief's three, plus `CLOSED` so that closing isn't a delete. |
| `accounts.branch_id` | Free text, e.g. `SG-ORCHARD-01`, required | The brief doesn't define branches. **Decide:** whether to seed a small fixed list instead. |
| `transactions.account_id` | Required | The brief lists only Client ID, but F4 and F5 need to know which account moved. We control the file format, so we include it. |
| `cases.category` | `TRANSACTION_DISPUTE`, `SERVICE_COMPLAINT`, `ACCOUNT_ISSUE`, `OTHER` | Same as the demo. |

**Decide**, the points that caused the most coupling in the demo:
1. Only `COMPLETED` transactions count for balances, risk signals and recommendation signals. The readers expose only those (A3 rule 6).
2. Erased clients: PII becomes NULL rather than placeholder text (a placeholder phone would fail the format check). This also frees the email and phone, so the person can come back later as a new client. Proposed: yes.
3. Whether `import_run_id` gets its foreign key now. Proposed: F3 adds it in their own migration when they create `import_runs`, so this migration doesn't wait for F3.

Feature tables (wealth cases, recommendation sets, products, risk profiles, interventions, import runs, audit events) are designed by each owner in their own migration. **Numbering:** plain sequential versions (`V3`, `V4`, …), taken in merge order. If two PRs pick the same number, the second to merge renumbers before merging; Flyway itself fails on a duplicate version, so CI catches it. Out-of-order mode stays off. This replaces the earlier idea of a number range per module, which would have needed out-of-order mode and could pass on laptops yet fail on a fresh Aurora database (a fresh database runs versions in number order, not merge order). CI already runs every migration against an empty database through Testcontainers, so a broken order fails the PR. If your local database ran a migration from a branch that later changed, reset it with `docker compose down -v`.

**Mapping rule for entities:** map other tables' IDs as plain `UUID` fields (`private UUID clientId;`), not as `@ManyToOne` to another module's entity. Rule B1.2 requires this anyway, and it avoids Hibernate rejecting the composite foreign keys (`account_id, client_id`), where the same column would otherwise be mapped twice. Note that `ddl-auto=validate` checks columns and types but not foreign keys, so the SQL is what enforces them.

### A3. Transaction file format (owner: F3)

The transaction server (the core-banking simulator) publishes one file per business day (Singapore date).

**Listing:** `GET /files?since=2026-10-01` returns a manifest:

```json
[{ "name": "transactions_2026-10-19.csv", "businessDate": "2026-10-19",
   "rows": 1240, "sizeBytes": 98213, "sha256": "9f2c…" }]
```

**Download:** `GET /files/{name}` returns the CSV. If the downloaded file's sha256 or row count doesn't match the manifest, the file is treated as corrupted and the whole file fails.

**File rules:** UTF-8, comma-separated, RFC 4180 quoting, LF line endings, and exactly this header:

```csv
transaction_id,client_id,account_id,type,amount,currency,occurred_at,status
TX-20261019-000001,0192f3a1-7c2e-7b10-9a4e-3f6d2c8b1a01,0192f3a2-0d4b-7e21-8c5f-6a7b9c0d1e02,DEPOSIT,5000.00,SGD,2026-10-19T09:15:00+08:00,COMPLETED
TX-20261019-000002,0192f3a1-7c2e-7b10-9a4e-3f6d2c8b1a01,0192f3a2-0d4b-7e21-8c5f-6a7b9c0d1e02,WITHDRAWAL,120.50,SGD,2026-10-19T13:02:41+08:00,PENDING
```

| Field | Rule |
|---|---|
| `transaction_id` | Required, at most 40 characters, unique across all files |
| `client_id`, `account_id` | UUIDs that must exist, and the account must belong to that client |
| `type` | `DEPOSIT` or `WITHDRAWAL` |
| `amount` | Positive, at most 2 decimal places, no thousands separator. The importer must check `BigDecimal.scale() <= 2` before inserting: the database column silently rounds `10.005` to `10.01`, and a `CHECK` can't catch it because rounding happens first |
| `currency` | `SGD` |
| `occurred_at` | ISO-8601 with an offset, not in the future |
| `status` | `COMPLETED`, `PENDING` or `FAILED` |

**Row rejection reasons:** these go into the import audit as codes plus the line number: `UNPARSEABLE`, `MISSING_FIELD`, `BAD_TYPE`, `BAD_AMOUNT`, `BAD_CURRENCY`, `BAD_TIMESTAMP`, `BAD_STATUS`, `UNKNOWN_CLIENT`, `UNKNOWN_ACCOUNT`, `ACCOUNT_CLIENT_MISMATCH`, `DUPLICATE_IN_FILE` and `CONFLICT`.

**Run status:** `SUCCESSFUL` if no row is rejected. `PARTIALLY_SUCCESSFUL` if at least one row is accepted and at least one is rejected. `FAILED` if the file is missing, corrupted, has the wrong header, or no row is accepted.

**How rows are written:** for each batch, the importer first selects the stored rows with those IDs, then classifies every row in Java as new, already imported (all fields identical), valid status change (only `status` differs and moves forward) or `CONFLICT` (anything else differs). That classification produces the run counts. It then writes only the new rows and the valid status changes with a JDBC batch, not JPA `save()`, which would issue a `SELECT` per row because the ID is assigned by the application. The counts can't come from the database's "rows affected", because an identical row and a conflicting row would both report 0. Only one import job runs at a time (a job lock in `shared.jobs`), so nothing changes between the select and the write.

**Re-imports and status changes:** a `transaction_id` that's already stored with identical fields is skipped and counted as `already imported` (it isn't counted as a rejection). If only `status` differs and it moves forward (`PENDING` → `COMPLETED` or `FAILED`), the row is updated. Any other difference is rejected as `CONFLICT`. **Decide:** whether to allow status changes at all, or treat every file as final.

## Part B: module interfaces and events (meeting 2)

### B1. Rules

1. **Each module's base package is its public API.** For example, `com.scrooge.crm.clients` holds the interfaces, records and events that other modules may use. Everything else (entities, repositories, controllers, services) goes in `clients.internal` and is off-limits to other modules. Spring Modulith enforces this with a test that fails the build on a violation or a dependency cycle:

   ```java
   @Test void modulesAreValid() { ApplicationModules.of(CrmApplication.class).verify(); }
   ```

   Modulith treats `shared` as a module too, so by default `shared.audit`, `shared.security` and the other sub-packages would count as its internals, and every other module using them would fail this test. Mark it open in `shared/package-info.java` (the skeleton doesn't have this file yet):

   ```java
   @ApplicationModule(type = ApplicationModule.Type.OPEN)
   package com.scrooge.crm.shared;
   ```

2. **Other modules never read your tables.** They call your interface. Records cross module boundaries, entities never do.
3. **Writes join the caller's transaction.** Spring's default `@Transactional` propagation does this, so the methods need no `tx` parameter (the NestJS draft had one). `AuditService.record` uses `Propagation.MANDATORY`, so calling it outside a transaction is an error rather than a silently separate commit. The exception is audit rows that must survive a rollback (access denials, failed imports), which use `recordStandalone` (see `shared.audit`). Audited reads run in a normal transaction (not `readOnly = true`) and use `record`, so a GET holds one database connection, not two.
4. **Dependencies only point one way.** This is the graph Modulith will check. Every module may also use `shared`, and `shared` uses no module.

   | Module | May call |
   |---|---|
   | `users` | nothing else |
   | `clients` | `users` |
   | `verification` | `clients`, `users` (reviewer assignment) |
   | `transactions` | `clients` |
   | `cases` | `clients`, `users`, `transactions` |
   | `retention` | `clients`, `users`, `transactions`, `cases` |
   | `recommendations` | `clients`, `transactions`, `cases` |

   Where something must call "upwards", the lower module defines a small interface and the higher one implements it. Three of these are below: `UserLookup`, `ActivationCheck` and `ErasureParticipant`.
5. **Every provider ships an in-memory fake and a contract test** in week 1, as in the original plan. The fake lives in `src/test/java` under the provider's package, and other modules' tests use it.
6. **Readers hide rows that don't count:** `TransactionReader` returns only `COMPLETED` rows, and `ClientDirectory` never returns erased clients unless asked.

### B2. Interfaces

Sketches. Names can change in the meeting, but each method's meaning should be agreed there.

**`shared.security` (owner: platform)**

```java
public interface CurrentUser {          // request-scoped, built from the JWT
    UUID id();
    Role role();                        // ADMIN, AGENT
    default boolean isAdmin() { return role() == Role.ADMIN; }
}

public interface UserLookup {           // implemented by `users`, so shared doesn't depend on it
    Optional<UserSummary> findByCognitoSub(String sub);   // the security filter rejects inactive users
}
```

**`shared.audit` (owner: data + audit)**

```java
public interface AuditService {
    // Creates, reads, updates and deletes: commits or rolls back together with the change.
    @Transactional(propagation = Propagation.MANDATORY)
    void record(AuditEntry entry);

    // Access denials and failed imports: its own transaction, so it is kept even when the caller
    // rolls back. Kept for rare events because it holds a second connection while it runs.
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    void recordStandalone(AuditEntry entry);
}

public record AuditEntry(
    String eventType,            // CLIENT_UPDATED, ACCESS_DENIED, IMPORT_COMPLETED ...
    Crud crud,                   // CREATE, READ, UPDATE, DELETE
    UUID actorId,                // null for scheduled jobs (shown as SYSTEM)
    UUID clientId,               // nullable
    String entityType, String entityId,
    List<FieldChange> changes,   // Update only; Create/Read/Delete store just the Client ID (Appendix 2)
    Map<String, Object> details  // feature-specific, stored as JSONB
) {}

public record FieldChange(String attribute, String before, String after) {}  // stored encrypted with the client's key
```

The brief's `"First Name|Address"` / `"LEE|ABC"` / `"TAN|XX"` format is derived from `changes` when the log is displayed, so the data stays structured.

Why two methods: if `ClientAccess` wrote `ACCESS_DENIED` with `record` and then threw, the rollback would delete the audit row along with everything else. Audited GETs must not use `@Transactional(readOnly = true)`, because Postgres rejects an `INSERT` in a read-only transaction.

**What the audit module must also cover** (owner: data + audit; settle in meeting 2):
- **Timestamps:** `AuditService` sets `occurred_at` itself from the shared `Clock`, in ISO-8601, so callers can't supply or fake it.
- **Real before and after values without breaking erasure:** the brief wants the actual old and new values ("LEE|ABC" → "TAN|XX"), and erasure must remove a client's PII. Masked values would fail the first requirement, and plain values would fail the second. Proposed: crypto-shredding. Each client gets a data key (envelope-encrypted with KMS on AWS, a local key in dev). `changes` and `details` are encrypted with it, and erasure deletes the key, so the rows stay but can no longer be read. Key lookup fails for an erased client rather than creating a new key, so nothing can quietly re-key them. Rows with no client (import runs, staff user changes, some access denials) are stored unencrypted: they hold no client PII. See D13.
- **Tamper resistance:** the application's database role gets only `INSERT` and `SELECT` on `audit_events`. Rows are inserted without a hash. A worker job then chains them in sequence order, each row storing a hash of itself plus the previous row's hash, and a `verify-audit-chain` command checks it. Chaining at insert time would need one global lock held until each business transaction commits, serialising every audited request, and a `recordStandalone` call inside such a transaction would wait on its own caller and hang. The hash covers the stored ciphertext, not the decrypted values, so the chain still verifies after crypto-shredding. Archived copies go to S3 with Object Lock.
- **F1 events from Cognito:** login, logout, MFA and password changes happen in Cognito, not in our API. A Cognito post-authentication trigger and the CloudTrail/Cognito event stream feed them into `audit_events` through the same service.
- **F3 import audit:** the import run is the audit subject. `details` carries start and end time, status, processed/accepted/rejected counts, and each rejected line with its reason code. Corrupted files, connection failures and exceptions get their own event types, written with `recordStandalone` so a rolled-back import still leaves its audit trail.

**`users` (owner: F1)**

```java
public interface UserDirectory {
    Optional<UserSummary> find(UUID userId);
    boolean isActiveAgent(UUID userId);     // used before assigning a client or case
    List<UserSummary> admins();               // F6 escalation emails
```

**`clients` (owner: F1 + F2 core)**

```java
public interface ClientDirectory {
    Optional<ClientSummary> find(UUID clientId);         // empty if erased
    List<UUID> idsForAgent(UUID agentId);
    UUID agentOf(UUID clientId);                       // throws ClientNotFoundException
    boolean hasRecoConsent(UUID clientId);
}

public interface ClientAccess {         // the ownership check every client-scoped endpoint calls
    void assertCanAccess(UUID clientId);   // admin: always; agent: own clients only.
                                             // Otherwise audits ACCESS_DENIED (recordStandalone) and throws (403)
}

public interface AccountService {
    List<AccountSummary> listForClient(UUID clientId);
    Optional<AccountSummary> find(UUID accountId);
    AccountSummary open(OpenAccount command);   // F4's "Accept, open account" uses source=RECOMMENDATION
}

public interface ActivationService {
    ActivationResult evaluate(UUID clientId);   // activates PENDING accounts when every check passes
}

public interface ActivationCheck {      // implemented by `verification`
    CheckResult check(UUID clientId); // PASSED, PENDING, FAILED, NOT_APPLICABLE
}
```

`ClientAccess` sits in `clients` rather than `shared.security` because it needs `ClientDirectory`. Putting it in `shared` would create a cycle.

`ActivationCheck` is how the wealth rule plugs in without a cycle. `ActivationService` runs the identity check itself, then every `ActivationCheck` bean. `verification` implements one ("high-value accounts need a verified wealth case") and calls `ActivationService.evaluate` after a reviewer decides. This replaces the NestJS draft's `WealthStatusReader`.

**`shared.erasure` (owner: data + audit)**

```java
public interface ErasureParticipant {
    void eraseClient(UUID clientId);   // each module scrubs its own tables, in the caller's transaction
    default void afterErasure(UUID clientId) {}   // non-database cleanup (S3 objects), after commit
}
```

Erasure is a synchronous call in one transaction: `clients` runs every participant, closes the client's accounts, clears its own PII, and deletes the client's audit data key (D13). It isn't an event, because a half-finished erasure is worse than a failed one. `ClientErased` is published afterwards. Its listener calls every participant's `afterErasure`, which deletes what a database transaction can't cover: NRIC images and Textract output in S3, and wealth evidence files. Because it runs through the event registry, it is retried until it succeeds.

**Backups:** Aurora snapshots taken before the erasure still hold the plain PII and the client's key. Erasure is therefore complete only once the backup retention period has passed, so set it deliberately (proposed: 7 days) and say so in the privacy notice. A restore from backup must re-apply erasures: keep an `erasure_log` of erased client IDs (an ID alone isn't PII) and replay it after any restore.

### B3. Events

Events are Java records in the emitter's base package. They carry IDs and small facts only, never PII, because they're stored and may go to SQS.

| Event | Emitted by | Fields | Consumers |
|---|---|---|---|
| `ClientCreated` | clients | `clientId`, `agentId` | none yet |
| `ClientUpdated` | clients | `clientId`, `Set<String> changedFields` | F4 marks recommendations outdated |
| `ClientIdentityChanged` | clients | `clientId`, `status` | F4 marks outdated (eligibility) |
| `ClientErased` | clients | `clientId` | caches |
| `AccountOpened` | clients | `accountId`, `clientId`, `type`, `source` | F4 marks outdated |
| `AccountStatusChanged` | clients | `accountId`, `clientId`, `from`, `to` | F4 marks outdated; F5 notes closures (churn signal) |
| `WealthCaseDecided` | verification | `wealthCaseId`, `clientId`, `outcome` | none required |
| `TransactionsImported` | transactions | `importRunId`, `Set<UUID> clientIds`, `latestOccurredAt` | F4 queues regeneration; F5 may run risk early |
| `CaseOpened` | cases | `caseId`, `clientId`, `category`, `transactionId` | F4 marks outdated (open cases lower scores) |
| `CaseStatusChanged` | cases | `caseId`, `clientId`, `from`, `to` | F4 marks outdated on resolve |
| `CaseEscalated` | cases | `caseId`, `clientId`, `assigneeId` | none required (F6 sends the email itself) |
| `RecommendationOutcomeRecorded` | recommendations | `clientId`, `recommendationId`, `outcome`, `accountId` | none required |

**How they're published and delivered.** This uses Spring Modulith instead of a hand-written outbox:

1. The emitter calls `events.publishEvent(new ClientUpdated(...))` inside its `@Transactional` method.
2. Modulith's event publication registry (`spring-modulith-starter-jdbc`) saves the event in the same transaction. It is the outbox. If the app dies before a listener finishes, the publication stays marked incomplete. It's only retried if we set `spring.modulith.events.republish-outstanding-events-on-restart: true` (off by default), or if a small scheduled job resubmits incomplete publications older than a few minutes. Proposed: the scheduled job, in the worker, because with several API tasks a restart of one would also republish events the others are still handling.
3. Consumers use `@ApplicationModuleListener`. It runs after the commit, asynchronously, in its own transaction.
4. Light work, such as marking a recommendation set outdated, happens right in the listener. Heavy work (F4's Bedrock regeneration, an early F5 risk run) must not happen in the API, so the listener only sends an SQS message and the worker does the work. Locally, that SQS is LocalStack, so it's the same code. Modulith can also do this automatically with `@Externalized` and `spring-modulith-events-aws-sqs`. **Decide** whether to use that or send the messages ourselves.
5. **Listeners must be idempotent**, because delivery can repeat. For example, "mark outdated" is naturally safe to repeat, and regeneration checks a per-client cooldown.

The registry's table comes from Modulith's own Postgres schema script. Copy it into a migration rather than letting Modulith create it at startup, so Flyway stays the only thing that changes the schema. Take the script from the 2.x `spring-modulith-events-jdbc` jar: 2.0 changed the table (status and attempt columns), so 1.x docs show the wrong shape. `@ApplicationModuleListener` runs asynchronously, so also add `@EnableAsync` on the application class (harmless if something else already enables it).

### B4. API and worker split (goes with step 3)

One jar, two Spring profiles:

| | `api` | `worker` |
|---|---|---|
| Web server | on | off (`spring.main.web-application-type=none`) |
| Controllers | yes | no |
| `@Scheduled` jobs, SQS consumers | no | yes (`@ConditionalOnProperty("crm.worker.enabled")`) |
| Event listeners | yes (light work and handing off to SQS) | yes (heavy work) |
| ECS scaling | on request count | on queue depth |

Locally, run the API from the IDE with `SPRING_PROFILES_ACTIVE=api,local`, and the worker with `worker,local`. For quick work, `api,worker,local` runs both in one process.
